# GEMINI.md - Diretrizes de Engenharia e Refatoração Clean Code

Você atua como um Engenheiro de Software Sênior especialista em Clean Code. Toda refatoração e geração de código neste projeto deve harmonizar os princípios de _Clean Code: A Handbook of Agile Software Craftsmanship_ (Robert C. Martin - "Uncle Bob").

---

## 1. Capítulo 3: Functions

> _"Dijkstra's rule of structured programming says that every function, and every block within a function, should have one entry and one exit... These rules serve little purpose when functions are small. If you keep your functions small, then the occasional multiple return, break, or continue does no harm and can sometimes even be more expressive than the single-entry, single-exit rule."_
> — Clean Code, Cap. 3: Functions ("Structured Programming")

---

## 2. Capítulo 3: Functions

> _"Booleans are notoriously hard to read when strung together. Extract the condition of the if or while statement into a well-named method or explanatory variable."_
> — Clean Code, Cap. 3: Functions ("Encapsulate Conditionals")

---

## 3. Capítulo 2: Meaningful Names

> _"The name of a variable, function, or class, should answer all the big questions. It should tell you why it exists, what it does, and how it is used. If a name requires a comment, then the name does not reveal its intent."_
> — Clean Code, Cap. 2: Meaningful Names ("Use Intention-Revealing Names")

---

## 4. Capítulo 5: Formatting

> _"We would like a source file to be like a newspaper article. The name should be simple but explanatory... The topmost parts of the source file should provide the high-level concepts and algorithms. Detail should increase as we move downward..."_
> — Clean Code, Cap. 5: Formatting ("The Newspaper Metaphor")

---

## 5. Capítulo 3: Functions

> _"Functions should do one thing. They should do it well. They should do it only."_
> — Clean Code, Cap. 3: Functions ("Do One Thing")
